# Xray VLESS + XHTTP + TLS через Traefik

Проект находится в активной разработке и ещё не использовался в продакшене. Скрипт `xray.py` отвечает за настройку, проверку конфигураций и пользователей; применение изменений и управление стеком выполняются через корневой `hctl`.

Клиент подключается к `xray.${DOMAIN}:443`, Traefik завершает TLS и передаёт XHTTP по h2c на внутренний порт Xray 8080. При открытии `https://xray.${DOMAIN}/` в браузере отображается статический сайт из отдельного контейнера Nginx. Порты Xray и Nginx на хост не публикуются.

```text
Клиент / браузер → TLS, TCP/443 → Traefik
                                 ├─ /api/... → h2c, TCP/8080 → Xray → Интернет
                                 └─ остальные пути → HTTP, TCP/8080 → Nginx → сайт
```

Это VLESS + XHTTP с обычным сертификатом вашего домена, а не маскировка под сторонний REALITY target. Между Traefik и Xray TLS нет: используйте общую Docker-сеть только для доверенных контейнеров. Домен и IP сервера видны провайдеру; защиты от любой блокировки и полной незаметности схема не гарантирует.

Префикс `/api/` зарезервирован за Xray: router прокси имеет приоритет 100, router сайта — 10. Случайный путь из JSON не нужно переносить в Compose. Путь `/api` без завершающего слеша относится к сайту; не размещайте файлы сайта внутри `/api/`. Маршрутизация не зависит от HTTP-метода или User-Agent.

## Структура проекта

```text
xray/
├── xray.py                  # Настройка, проверка и пользователи
├── src/                     # Внутренний Python-код
│   ├── cli.py               # Команды и обработка ошибок
│   ├── compose.py           # Вызовы Docker Compose
│   ├── configuration.py     # Раздельные генераторы сервера и клиента
│   ├── users.py             # Реестр и операции с пользователями
│   └── storage.py           # Запись, права доступа и блокировка
├── tests/                   # Модульные и интеграционные проверки
├── compose.yaml
├── nginx/
├── site/
├── template.env
├── .env                     # Локальные настройки, не в Git
└── *_data/                  # Локальные данные и реквизиты, не в Git
```

Python-модули из `src/` не запускаются отдельно; устанавливать пакет через pip или создавать виртуальное окружение не требуется. Далее команды приводятся для рабочего каталога `available/xray`, кроме явно отмеченных проверок разработки из корня репозитория.

## Подготовка Traefik и DNS

Используйте работающий стек `available/traefik`. В нём уже объявлены:

- HTTPS entrypoint `websecure` на TCP/443;
- resolver `letsencrypt` с DNS challenge Cloudflare;
- Docker provider и внешняя сеть `traefik`.

Менять статическую конфигурацию Traefik для Xray не требуется. DNS API token для выпуска сертификата настраивается в `.env` **Traefik**, в переменной `CLOUDFLARE_API_TOKEN`, а не в `.env` Xray. Он должен иметь права на DNS challenge нужной зоны. Серое облако не мешает выпуску сертификата через DNS challenge.

Если ваш базовый домен — `example.com`, создайте DNS-запись:

| Тип | Имя | Значение | Проксирование Cloudflare |
|---|---|---|---|
| A | `xray` | Публичный IPv4 сервера с Traefik | **DNS only, серое облако** |

Не добавляйте AAAA, если IPv6 не настроен на этом сервере. Удалите или исправьте старую AAAA-запись: иначе часть клиентов будет обращаться не туда. TCP/443 должен быть доступен извне и опубликован **только Traefik**, а не Xray. Дополнительные порты для Xray в firewall открывать не нужно.

Убедитесь, что общие сети существуют:

```bash
docker network inspect traefik
docker network inspect apprise_notification
```

Если сеть отсутствует, создайте соответствующую командой `docker network create ИМЯ_СЕТИ`. Traefik должен быть подключён именно к сети `traefik`. Для уведомлений Restic нужен общий сервис Apprise.

## Настройки .env

| Переменная | Назначение |
|---|---|
| `CONTAINER_NAME` | Обязательное имя экземпляра, например `xray`; контейнер будет `xray_main` |
| `DOMAIN` | Обязательный базовый домен, например `example.com`; публичное имя автоматически станет `xray.example.com` |
| `RESTIC_PASSWORD` | Обязательный непустой пароль репозитория Restic; задайте случайный и сохраните отдельно |
| `TZ` | Часовой пояс расписания Restic, по умолчанию `Europe/Moscow` |

В `DOMAIN` не указывайте `https://`, порт, путь, завершающую точку и префикс `xray.`. Для IDN используйте ASCII/Punycode. Значение должно совпадать с вашей DNS-зоной; `example.com` в шаблоне нужно заменить.

`python3 xray.py setup` получает параметры через `docker compose config`, не исполняя `.env` как shell-код. Переменные окружения имеют приоритет над `.env`; сохраняйте постоянные настройки в `.env`, чтобы генерация и последующий запуск использовали один домен и имя контейнера.

Изменение `.env` не переписывает существующий JSON. Реестр сохраняет `DOMAIN`: при несовпадении операции пользователей и `check` отклоняются. Смену домена выполняйте отдельно, согласованно обновляя `.env`, поле `domain` в реестре, DNS и выданные клиентские профили (адрес, SNI и Host); перед этим сохраните резервную копию. Имена router/service `xray` и `xray-site` глобальны для Docker provider Traefik: этот шаблон рассчитан на один такой стек на экземпляр Traefik.

## Первая установка

Нужны Linux, Python 3.10+, Docker Engine, Compose с поддержкой `config --format json`, `run --pull never` и `up --wait`, а также клиент с поддержкой **VLESS + XHTTP + TLS**. Для запуска `hctl` установите Fish и Gum. Python-код использует только стандартную библиотеку, включая Linux-механизмы блокировки и открытия файлов без перехода по ссылкам; curl и внешний сервис определения IP для генерации не требуются. Сохраняйте структуру каталогов репозитория: Compose использует общий шаблон `available/restic/restic-compose-base.yaml`.

1. Создайте DNS-запись `xray.ваш-домен` на IP сервера. В Cloudflare оставьте **DNS only — серое облако**. Если IPv6 не настроен, не добавляйте AAAA.
2. Из `available/xray` выполните `cp template.env .env` и `chmod 600 .env`. Укажите базовый `DOMAIN` без `xray.` и задайте случайный `RESTIC_PASSWORD`.
3. Выполните:

   ```bash
   docker compose config --quiet
   mkdir -p ../../enabled
   ../../hctl enable xray
   ../../hctl pull xray
   python3 xray.py setup
   python3 xray.py users create phone
   python3 xray.py check
   ../../hctl up xray
   ../../hctl ps xray
   ```

`setup` создаёт только `${CONTAINER_NAME}_data/config/config.json` с пустым списком `clients` и `${CONTAINER_NAME}_data/users.json` с пустым реестром. `users create phone` отдельно создаёт пользователя с новым UUID. Без пользователей сервер не предоставляет клиентский доступ.

Показать параметры подключения или импорт-ссылку:

```bash
python3 xray.py users show phone
python3 xray.py users show phone --format link
```

Чтобы сохранить профиль для устройства с Xray (пример для `CONTAINER_NAME=xray`):

```bash
umask 077
mkdir -p xray_data/client
python3 xray.py users show phone --format json > xray_data/client/phone.json
```

Проверьте успешное завершение команды перед передачей файла. JSON и ссылка формируются по запросу, отдельные файлы для пользователей автоматически не создаются. Перенесите JSON на устройство с Xray или импортируйте ссылку в клиент с поддержкой XHTTP и TLS. Клиент проверяет сертификат; не включайте `allowInsecure`.

`hctl enable xray` регистрирует стек ссылкой в `enabled/`, но не запускает его. Имя `xray` здесь — имя каталога стека, независимо от значения `CONTAINER_NAME`. `hctl pull xray` скачивает образы всех сервисов стека, включая Nginx и Restic.

`setup` настраивает сервер без пользователей и проверяет только Xray; `check` проверяет согласованность реестра, Compose, Xray и Nginx без генерации. Изменения пользователей проверяются Xray на отдельном кандидатном JSON **до** замены постоянной конфигурации. Эти проверки используют только локальные образы (`--pull never`) и одноразовые контейнеры, но не управляют постоянными сервисами. После `../../hctl up xray` выпуском и продлением сертификата занимается Traefik. Дождитесь успешного выпуска, прежде чем проверять подключение клиента.

Клиент использует SNI и HTTP Host `xray.${DOMAIN}`, ALPN `h2,http/1.1` и режим XHTTP `packet-up` для совместимости с reverse proxy. Сервер принимает XHTTP в режиме `auto`; путь и UUID клиента совпадают с серверными. Не добавляйте buffering, переписывание пути, BasicAuth или обязательную авторизацию веб-панели к router Xray: это нарушит протокол. Клиентский UUID остаётся средством аутентификации VLESS.

## Настройка и управление

`python3 xray.py` отвечает за настройку, проверку Xray и сохранённый список пользователей. Управление стеком выполняется через корневой `hctl`; из `available/xray` он вызывается как `../../hctl`. Команды можно вызывать из любого рабочего каталога, указав путь к скрипту: Docker запускается из каталога стека.

Справка: `python3 xray.py --help` и `python3 xray.py КОМАНДА --help`; для неё Docker и `.env` не нужны. Скрипт также можно запускать как `./xray.py`. Стандартные переменные окружения Compose, в том числе `COMPOSE_PROJECT_NAME` и `COMPOSE_FILE`, сохраняют своё действие: используйте одинаковое окружение при настройке, проверке и управлении стеком.

| Команда | Назначение |
|---|---|
| `setup` | Создать сервер без пользователей и проверить Xray, не запуская стек |
| `check` | Проверить реестр, Compose, Xray и Nginx без перегенерации |
| `users create ИМЯ` | Создать пользователя с уникальным UUID |
| `users list` | Показать имена и сохранённые состояния без UUID и ссылок |
| `users show ИМЯ` | Показать параметры подключения и VLESS-ссылку |
| `users show ИМЯ --format json` | Вывести только клиентский JSON в stdout |
| `users show ИМЯ --format link` | Вывести только VLESS-ссылку в stdout |
| `users suspend ИМЯ` | Исключить UUID из активных `clients`, сохранив реквизиты |
| `users resume ИМЯ` | Вернуть доступ с прежним UUID |
| `users delete ИМЯ [--yes]` | Удалить запись; без `--yes` требуется ответ `да` |
| `users import ИМЯ` | Импортировать единственного пользователя прежней установки |

Имя — 1–64 латинских буквы, цифры, `_` или `-`, первый символ — буква или цифра. Имена регистрозависимы. Повторное создание имени и операции с отсутствующим пользователем отклоняются. Повторные `suspend` и `resume` сохраняют тот же UUID.

### Применение изменений пользователей

Команды `users` **не используют API Xray и не перезапускают сервисы**. После изменений выполните из `available/xray`:

```bash
python3 xray.py check
../../hctl restart xray
```

До перезапуска Xray использует прежний список: созданный пользователь ещё не получает доступ, а приостановленный или удалённый ещё не теряет его. `list` и `show` показывают **сохранённое**, а не работающее состояние; инструмент не отслеживает факт применения. Можно накопить несколько изменений и применить их одним перезапуском. Если стек ещё не запущен, после `check` используйте `../../hctl up xray`.

Приостановка — логика этого инструмента, не отдельный флаг Xray: запись остаётся в реестре, но исключается из серверного `clients`. После `resume` прежние клиентские настройки снова подходят. Удаление убирает запись окончательно; повторное создание того же имени выдаёт новый UUID. Ранее экспортированные файлы и ссылки инструмент не удаляет. После перезапуска старый UUID удалённого пользователя больше не предоставляет доступ.

### Переход с прежней установки

Не запускайте `setup` повторно. Сначала сохраните резервную копию каталога данных, затем выполните:

```bash
python3 xray.py users import legacy
python3 xray.py check
../../hctl restart xray
```

Импорт рассчитан на прежний комплект этого инструмента: один пользователь в `config/config.json` и соответствующий `client/client.json`. UUID, XHTTP-путь и поля существующего серверного пользователя сохраняются; старые клиентские файлы не меняются. Несовпадение UUID, пути или домена отклоняется. При наличии реестра повторный импорт запрещён. До импорта команды пользователей не заменяют прежние реквизиты автоматически; обычный `check` доступен и для прежней конфигурации.

Команды управления принадлежат только `hctl`:

| Команда из `available/xray` | Назначение |
|---|---|
| `../../hctl up xray` | Запустить стек в фоне с ожиданием готовности (`--wait`) |
| `../../hctl down xray` | Остановить и удалить контейнеры стека без удаления данных |
| `../../hctl restart xray` | Остановить стек через `down` и запустить заново |
| `../../hctl pull xray` | Скачать образы всех сервисов стека |
| `../../hctl ps xray` | Показать состояние контейнеров |
| `../../hctl logs xray` | Показать логи всего стека |

`hctl` принимает имена стеков, не сервисов; параметры `--tail`, `--follow`, `--force-recreate` и выбор отдельных сервисов через него сейчас недоступны. Для однозначного выбора всегда указывайте `xray`: многие команды без имени применяются ко всем включённым стекам. Перезапуск затрагивает весь стек и прерывает подключения. Запуск сервисов Restic сохраняет их штатное поведение, включая проверку репозитория при запуске.

`check` не проверяет DNS, сертификат или сквозное соединение клиента. Само изменение Python-кода не требует перезапуска сервисов. После изменения конфигураций используйте `check`, а затем подходящую команду `hctl`; повторный `setup` не является способом обновления.

Ошибки Docker при настройке и проверке выводятся без содержимого конфигураций; ненулевой код передаётся вызывающему процессу (коды вне диапазона 1–125 заменяются на 1). Логи через `hctl` содержат исходный вывод контейнеров: не публикуйте его без проверки на реквизиты.

## Статический сайт

Заглушка находится в `site/index.html`, конфигурация Nginx — в `nginx/default.conf`. Каталог сайта и конфигурация смонтированы только для чтения; Nginx работает без привилегий, с read-only корневой файловой системой и временным `/tmp`. EntryPoint образа заменён прямым запуском Nginx, чтобы стартовые скрипты не пытались менять конфигурацию.

Для изменения содержимого отредактируйте файлы в `site/`: обычные изменения файлов доступны без пересборки образа. После изменения конфигурации выполните:

```bash
python3 xray.py check
../../hctl restart xray
```

Это проверяет оба сервиса и перезапускает весь стек, а не только Nginx: текущий `hctl` не поддерживает выбор отдельных сервисов.

Отсутствующие файлы возвращают `404`, листинг каталогов отключён. Монтируется только каталог `site/`, а не весь стек или каталог данных. Не копируйте туда `.env`, JSON, UUID и импорт-ссылки: содержимое сайта публично. Сайт и прокси запускаются независимо; отказ одного backend не должен нарушать работу другого.

## Данные и безопасность

Для `CONTAINER_NAME=xray` структура и права такие:

```text
xray_data/                    # 700
├── config/                   # 755
│   └── config.json           # 644, содержит UUID активных пользователей
├── users.json                # 600, DOMAIN, имена, UUID и состояния
└── client/                   # Необязательные экспорты и прежние профили
    └── phone.json            # Создаётся вручную через show; используйте umask 077
```

Серверный JSON читает непривилегированный процесс контейнера через read-only bind mount; родительский каталог закрыт для других обычных пользователей хоста. Контейнер сохраняет ограничения `read_only`, `no-new-privileges`, `cap_drop: ALL` и временный `/tmp`. Отсутствующий JSON не заменяется автоматически каталогом.

Не публикуйте JSON, ссылки, реестр и `.env`: в них данные доступа. Каталоги `*_data` исключены из Git; не сохраняйте экспорты в публичный `site/`. `show` намеренно раскрывает реквизиты, а предупреждение отправляет в stderr, чтобы stdout оставался пригодным для экспорта. Даже приостановленные UUID являются секретами: после возобновления они снова работают.

Повторный `setup` останавливается при наличии серверного JSON, реестра, журнала операции или любого из двух прежних клиентских файлов, включая повреждённую символьную ссылку. Если проверка Xray после настройки завершилась ошибкой, исправьте причину и выполните `check` — не удаляйте реквизиты ради повторного запуска `setup`.

`setup`, `check` и команды `users` используют общую неблокирующую блокировку `.xray.lock`: второй одновременный запуск завершается ошибкой. Файл исключён из Git и остаётся после завершения команды; наличие файла само по себе не означает активную блокировку. Не удаляйте его во время работы команды. Символьные ссылки в каталогах и файлах данных запрещены. Блокировка согласует операции этого инструмента, но не защищает от ручного изменения данных, `hctl` или резервного копирования другим процессом: не выполняйте их одновременно с изменениями пользователей.

При первичном `setup` ошибка записи может оставить часть файлов; они сохраняются для проверки и ручного восстановления. При отказе теста Xray после `setup` (в том числе из-за отсутствия локального образа) серверный JSON и реестр остаются на месте. После исправления используйте `check`, а не повторную генерацию.

При изменении пользователей отказ проверки кандидатного JSON оставляет постоянные файлы нетронутыми. Серверный JSON и реестр заменяются атомарно каждый по отдельности; для согласования двух замен используется закрытый журнал `.users-transaction.json`. Если запись прервалась, **не перезапускайте стек**: выполните `users list` или `check`. Следующая команда откатит оба файла к прежнему состоянию и завершится ошибкой с сообщением о восстановлении; после этого повторите нужную операцию. Повреждённый журнал не применяется — требуется ручное восстановление из резервной копии. Не удаляйте журнал вручную, пытаясь продолжить операцию.

Не редактируйте `clients` вручную: несовпадение с реестром блокирует операции и `check`. Остальные серверные настройки сохраняются при изменении пользователей. Из-за атомарной замены JSON не полагайтесь на старое файловое bind-монтирование: применяйте изменения именно через `hctl restart xray`, который пересоздаёт контейнеры через `down` и `up`.

## Проверки и обслуживание

```bash
python3 xray.py check
../../hctl logs xray
```

При `DOMAIN=example.com` проверьте DNS и сертификат (без отключения проверки сертификата):

```bash
dig +short xray.example.com A
dig +short xray.example.com AAAA
curl -v --connect-timeout 10 https://xray.example.com/
curl -I --connect-timeout 10 https://xray.example.com/
curl -i --connect-timeout 10 https://xray.example.com/missing-file.txt
```

На `/` ожидается `200` с HTML-заглушкой (для HEAD — без тела), на отсутствующий файл — `404` от Nginx. Для проверки статических ресурсов добавьте файл в `site/` и запросите его URL. Случайный несуществующий путь `/api/...` должен обрабатываться Xray, а не возвращать HTML-заглушку; один лишь статус `404` не доказывает правильность выбора backend.

Успешная TLS-проверка и даже ответ HTTP не доказывают работу прокси. При ошибке сертификата смотрите логи **контейнера Traefik** и права DNS API token. `502` на сайте указывает на Nginx или сеть; для `/api/...` — на внутренний порт 8080, h2c, конфигурацию Xray или сеть `traefik`. JSON-тест не проверяет DNS, сертификат и доставку трафика.

На клиентском устройстве запустите Xray с экспортированным профилем, например `phone.json`, затем:

```bash
curl --proxy socks5h://127.0.0.1:10808 https://ifconfig.me
```

В ответе должен быть внешний IP сервера Xray. Для временной диагностики измените серверный `log.loglevel` с `none` на `warning`, выполните `python3 xray.py check`, `../../hctl restart xray` и `../../hctl logs xray`. После проверки верните `none`, снова проверьте конфигурацию и перезапустите стек. Не публикуйте UUID и случайный путь в логах или скриншотах; access log Traefik, если его включить, может записывать путь XHTTP.

На тестовом стенде проверьте одновременную загрузку сайта и работу сгенерированного клиентского профиля. Проверки отказа отдельных backend требуют отдельной стендовой процедуры: текущий `hctl` управляет стеком целиком и не позволяет останавливать только `app` или `site`.

Watchtower для Xray разрешён меткой `com.centurylinklabs.watchtower.enable: "true"`. Автоматическое обновление произойдёт, если работающий Watchtower настроен обрабатывать этот контейнер. `latest` — изменяемый тег, возможны несовместимые изменения; Watchtower не выполняет описанные здесь проверки совместимости и резервное копирование перед обновлением. Для обновлений только вручную сначала отключите метку. Ручное обновление выполняйте после резервного копирования и проверки совместимости клиентов:

```bash
../../hctl pull xray
python3 xray.py check
../../hctl up xray
```

`pull` и `up` здесь относятся ко всему стеку, включая Nginx и Restic, а не только к Xray.

## Резервное копирование

Restic сохраняет весь `${CONTAINER_NAME}_data`, включая настройки клиентов. Репозиторий — `/backup/ssd/restic/${CONTAINER_NAME}_backups`, каталог восстановления — `${CONTAINER_NAME}_data/backup_restore`. `.env` и пароль храните отдельно. Сертификат находится у Traefik, не у Xray: резервное копирование его ACME-хранилища нужно проверить и настроить отдельно в стеке Traefik.

Каталоги `site/` и `nginx/` находятся в Git, вне `${CONTAINER_NAME}_data`, и в эту копию Restic не входят. Штатные файлы восстанавливаются из репозитория. Если меняете содержимое сайта только на сервере, организуйте его отдельное резервное копирование. Restic не останавливает контейнер сайта.

**Restic останавливает `${CONTAINER_NAME}_main` на время копирования и разрывает активные подключения.** Копирование запланировано на 03:30, очистка на 04:00 и проверка на 05:15 по `TZ`; проверка также выполняется при запуске своего сервиса. Общий шаблон использует Docker socket с привилегированным доступом к Docker хоста. При восстановлении сначала остановите стек, восстановите данные и права доступа, проверьте JSON и лишь затем запускайте сервисы. Не запускайте генерацию поверх восстановленных данных.

## Проверки разработки

Тесты запускаются из корня репозитория. Временные данные размещаются в `/tmp/opencode`; создайте этот каталог заранее, если его нет:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s available/xray/tests -v
git diff --check
```

При установленном Ruff дополнительно выполните `ruff check available/xray` и `ruff format --check available/xray`. Ruff нужен только для разработки, не для установки или управления стеком.

`test_cli.py`, `test_configuration.py`, `test_storage.py`, `test_users.py` и `test_project.py` — модульные и локальные проверки без Docker и сети. `test_setup.py` — отдельная интеграционная группа с настоящим разбором Compose, без скачивания образов и запуска контейнеров. Без Docker CLI эта группа пропускается; если CLI установлен, нужен и плагин Compose.

Например, интерфейс можно проверить отдельно:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s available/xray/tests -p test_cli.py -v
```

Проверяются независимость `setup` от создания пользователей, несколько пользователей, уникальность UUID, приостановка и возобновление без смены UUID, удаление с подтверждением, импорт прежних реквизитов, отказ проверки и восстановление после сбоя записи. Также проверяются TLS-настройки, импорт-ссылка, маршруты Traefik, отсутствие опубликованных портов, read-only монтирования, права файлов, защита существующих реквизитов и конкурентная блокировка. Ошибки Docker и команды настройки проверяются с подменой вызовов. Формат генерируемого пути `/api/<24 hex>` проверяется тестом генератора; тест структуры контролирует отсутствие Bash-файлов и единственную точку входа в корне.

На отдельном стенде дополнительно выполните первую установку с тестовым `.env`, создание двух пользователей, проверку конфигураций через `xray.py` и запуск через `hctl`. Проверьте оба профиля; затем приостановку, возобновление и удаление одного пользователя с ручным `check` и `hctl restart` после изменений. Убедитесь, что второй профиль продолжает работать после каждого перезапуска. Nginx, реальную маршрутизацию HTTP, выпуск сертификата, сквозное подключение через ваш домен и восстановление Restic проверяйте только на таком стенде. Автоматические тесты не подтверждают эти внешние интеграции.
