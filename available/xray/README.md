# Xray VLESS + XHTTP + REALITY

Прокси без панели управления на образе `ghcr.io/xtls/xray-core:latest`. Сервис Compose — `app`, имя контейнера — `${CONTAINER_NAME}_main`. REALITY принимает подключения напрямую, без Traefik и TLS-терминации. По умолчанию внешний порт — TCP/443, target/SNI — `www.bing.com`.

## Требования

- Linux VPS с публичным IPv4, Docker Engine и Compose с поддержкой `config --format json`, Python 3, curl.
- Свободный внешний TCP-порт, открытый в firewall и панели VPS.
- Общий шаблон `available/restic/restic-compose-base.yaml`: сохраняйте структуру каталогов репозитория, не копируйте только папку Xray.
- Внешняя Docker-сеть `apprise_notification`. Для уведомлений о сбоях резервного копирования нужен общий сервис Apprise.
- Клиент с поддержкой **VLESS + XHTTP + REALITY**.

**Если Traefik уже занимает 443 на том же IP, выберите другой `XRAY_PORT` или отдельный IP.** Подключать Xray к HTTP-router Traefik не нужно. Совместное использование 443 через TCP-маршрутизацию здесь не настраивается.

## Настройки

Скопируйте `template.env` в `.env` только при первой установке, затем отредактируйте:

| Переменная | Назначение |
|---|---|
| `CONTAINER_NAME` | Обязательное имя экземпляра, например `xray`. Латинские буквы, цифры, `_`, `-`; первый символ — буква или цифра |
| `XRAY_PORT` | Внешний TCP-порт, от 1 до 65535, по умолчанию 443 |
| `TARGET_HOST` | DNS-имя REALITY target/SNI, по умолчанию `www.bing.com` |
| `SERVER_IP` | IPv4 сервера; пустое значение включает определение через `api.ipify.org` |
| `RESTIC_PASSWORD` | Обязательный непустой пароль репозитория резервных копий; задайте случайный и сохраните отдельно |
| `TZ` | Часовой пояс расписания Restic, по умолчанию `Europe/Moscow` |

`setup.sh` получает настройки через Docker Compose, не исполняя `.env` как shell-код. Переменные окружения имеют приоритет над `.env`. **Имя контейнера и внешний порт лучше хранить в `.env`**, чтобы генерация и последующие команды запуска использовали одинаковые значения. `.env` не является шаблоном для уже созданных JSON: изменение SNI, IP или порта не обновляет автоматически существующие клиентские настройки.

Внутри контейнера порт всегда 443. `XRAY_PORT` записывается в клиентский JSON и импорт-ссылку. `TARGET_HOST` — не адрес прокси: клиент подключается к `SERVER_IP`, а домен используется REALITY. Перед выбором другого target проверьте совместимость TLS и сетевую доступность; `target`, `serverNames` и клиентский SNI должны соответствовать друг другу.

## Первая установка

Все команды выполняются из `available/xray`:

```bash
cp template.env .env
chmod 600 .env
# Отредактируйте .env, обязательно задайте RESTIC_PASSWORD.
```

Если внешней сети ещё нет, один раз создайте её:

```bash
docker network create apprise_notification
```

Затем проверьте настройки и сгенерируйте конфигурацию:

```bash
docker compose config --quiet
./setup.sh
docker compose up -d
docker compose ps
```

Скрипт скачивает образ, генерирует ключи и проверяет серверный JSON одноразовым контейнером, но **не запускает постоянные сервисы**. Он поддерживает вывод `xray x25519` с `PrivateKey:` / `Password (PublicKey):` и `Private key:` / `Public key:`. Неизвестный формат отклоняется без печати ключей.

Для разового указания адреса при первой генерации:

```bash
SERVER_IP=203.0.113.10 ./setup.sh
```

Это документационный IP — замените его своим. При неверном автоопределении можно вместо этого сохранить адрес в `.env`.

## Данные и права доступа

При `CONTAINER_NAME=xray` создаётся:

```text
xray_data/                    # 700, доступ только владельцу на хосте
├── config/                   # 755
│   └── config.json           # 644, содержит приватный ключ сервера
└── client/                   # 700
    ├── client.json           # 600, SOCKS5 на 127.0.0.1:10808
    └── import-link.txt       # 600, ссылка vless://
```

Серверный JSON читается непривилегированным процессом контейнера через read-only bind mount; закрытый родительский каталог защищает его от других обычных пользователей хоста. Отсутствующий файл не заменяется автоматически каталогом. Сохраняются `read_only`, временный `/tmp`, `no-new-privileges` и `cap_drop: ALL`.

Не публикуйте JSON, импорт-ссылку и `.env`. Они исключены из Git, включая старые каталоги `config/` и `client/`. Файлы клиента перенесите на клиентское устройство или импортируйте ссылку в совместимое приложение. В Happ при замене подключения удалите старое и импортируйте новую ссылку.

Повторная генерация останавливается, если существует любой из трёх файлов. При наличии старого `config/config.json` скрипт требует миграцию, а не создаёт новые ключи. Если проверка Xray завершилась ошибкой после генерации, исправьте сохранённый конфиг и повторите проверку вручную — удалять ключи и снова запускать генерацию не нужно.

## Резервное копирование

Сервисы `backup_restic__xray`, `prune_restic__xray` и `check_restic__xray` наследуют общий шаблон Restic. Сохраняется весь `${CONTAINER_NAME}_data`, включая серверный ключ и настройки клиентов. Репозиторий расположен в `/backup/ssd/restic/${CONTAINER_NAME}_backups`, каталог восстановления — в `${CONTAINER_NAME}_data/backup_restore`.

`RESTIC_PASSWORD` обязателен для всех команд Compose: небезопасное значение `123` из общего шаблона не используется. `.env` в снимок не входит — храните его и пароль отдельно в защищённом месте. Без исходного пароля зашифрованный репозиторий восстановить нельзя.

**На время резервного копирования Xray останавливается, активные подключения разрываются.** Расписание из общего шаблона: копирование в 03:30, очистка в 04:00 и проверка в 05:15 в часовом поясе `TZ`. При запуске сервиса проверки проверка также выполняется сразу. Шаблон использует Docker socket для управления контейнером; даже read-only mount сокета даёт привилегированный доступ к Docker на хосте.

После восстановления сохраняйте исходные ключи и права каталогов, не запускайте `setup.sh` повторно. Перед заменой работающих данных остановите стек, затем проверьте восстановленный конфиг и запустите сервисы.

## Миграция с docker-compose.yml

1. Сохраните защищённую копию старых `config/` и `client/`. **До обновления файлов репозитория** остановите старый стек:

   ```bash
   docker compose -f docker-compose.yml down
   ```

   Если обновление уже выполнено и старый Compose-файл исчез, отдельно остановите и удалите именно старый контейнер `xray-private` (`docker stop xray-private`, затем `docker rm xray-private`), предварительно убедившись, что это нужный контейнер. Не оставляйте его работающим рядом с новым.

2. Обновите файлы репозитория, создайте `.env` из шаблона, задайте имя и пароль Restic. Для сохранения клиентских настроек оставьте прежний IP и внешний порт 443. Проверьте наличие внешней сети `apprise_notification`.

3. Перенесите данные без изменения содержимого. Ниже пример для `CONTAINER_NAME=xray`; при другом имени замените значение `DATA`. Блок выполняется в отдельной оболочке и останавливается, если каталог назначения уже существует:

   ```bash
   (
     set -eu
     DATA=xray_data
     test -f config/config.json
     test -d client
     test ! -e "$DATA"
     test ! -L "$DATA"
     mkdir -m 700 "$DATA"
     mv config client "$DATA/"
     chmod 755 "$DATA/config"
     chmod 644 "$DATA/config/config.json"
     chmod 700 "$DATA/client"
     chmod 600 "$DATA/client/client.json" "$DATA/client/import-link.txt"
   )
   ```

4. Проверьте конфигурацию и запустите новый стек:

   ```bash
   docker compose config --quiet
   docker compose run --rm --no-deps app run -test -c /etc/xray/config.json
   docker compose up -d
   docker compose ps
   ```

**`setup.sh` при миграции запускать не нужно.** UUID, ключи, shortId и путь XHTTP остаются прежними. При изменении внешнего порта отдельно обновите порт в клиентском JSON и импорт-ссылке, не перевыпуская ключи.

## Диагностика и обновления

```bash
docker compose run --rm --no-deps app run -test -c /etc/xray/config.json
docker compose logs --tail=50 app
sudo ss -lntp | grep ':443'  # замените на выбранный внешний порт
curl -Iv --connect-timeout 10 https://www.bing.com/
```

Для диагностики временно измените `${CONTAINER_NAME}_data/config/config.json` → `log.loglevel` с `none` на `warning`, выполните `docker compose up -d --force-recreate app` и `docker compose logs --since=2m app`. Верните `none` после тестирования. По умолчанию сервер не ведёт логи, доступ через прокси к приватным IP-диапазонам заблокирован.

На клиентском устройстве запустите Xray с `client.json` и проверьте SOCKS5:

```bash
curl --proxy socks5h://127.0.0.1:10808 https://ifconfig.me
```

Успешный тест конфигурации не гарантирует TLS-рукопожатие или обход DPI. `www.bing.com` — стартовый target, не гарантия работы на любом VPS; поддержка XHTTP и импорт-ссылок зависит от клиента. Провайдер видит IP VPS и метаданные трафика, полной незаметности нет.

Watchtower для `app` явно отключён: `latest` изменяемый и может указывать на pre-release. Перед ручным обновлением проверьте совместимость версии сервера и клиента и сохраните резервную копию:

```bash
docker compose pull app
docker compose run --rm --no-deps app run -test -c /etc/xray/config.json
docker compose up -d app
```

Для чистой переустановки с новыми ключами остановите старый стек и используйте отдельный каталог установки; не смешивайте старые и новые файлы. На одном IP внешний порт может занимать только один слушающий сервис.

## Проверки разработки

Из корня репозитория; нужен Docker CLI с Compose, но демон и запуск контейнеров не требуются. Тесты используют временные каталоги в `/tmp/opencode` (создайте каталог заранее, если его нет):

```bash
bash -n available/xray/setup.sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s available/xray/tests -v
git diff --check
```

Docker Compose разбирает настоящий YAML, а скачивание образа, генерация ключей и тест Xray подменены. Проверяются настройки, порты, права, защита от перезаписи, обработка ошибок и наследование Restic. Реальное подключение клиента и восстановление резервной копии проверяйте отдельно на тестовом стенде.
