# Xray VLESS + XHTTP + TLS через Traefik

Клиент подключается к `xray.${DOMAIN}:443`, Traefik завершает TLS и передаёт XHTTP по h2c на внутренний порт Xray 8080. При открытии `https://xray.${DOMAIN}/` в браузере отображается статический сайт из отдельного контейнера Nginx. Порты Xray и Nginx на хост не публикуются. REALITY больше не используется.

```text
Клиент / браузер → TLS, TCP/443 → Traefik
                                 ├─ /api/... → h2c, TCP/8080 → Xray → Интернет
                                 └─ остальные пути → HTTP, TCP/8080 → Nginx → сайт
```

Это VLESS + XHTTP с обычным сертификатом вашего домена, а не маскировка под сторонний REALITY target. Между Traefik и Xray TLS нет: используйте общую Docker-сеть только для доверенных контейнеров. Домен и IP сервера видны провайдеру; защиты от любой блокировки и полной незаметности схема не гарантирует.

Префикс `/api/` зарезервирован за Xray: router прокси имеет приоритет 100, router сайта — 10. Случайный путь из JSON не нужно переносить в Compose. Путь `/api` без завершающего слеша относится к сайту; не размещайте файлы сайта внутри `/api/`. Маршрутизация не зависит от HTTP-метода или User-Agent.

## Структура проекта

```text
xray/
├── xray.py                  # Единственный управляющий скрипт в корне
├── src/                     # Внутренний Python-код
│   ├── cli.py               # Команды и обработка ошибок
│   ├── compose.py           # Вызовы Docker Compose
│   ├── configuration.py     # Генератор конфигураций
│   ├── storage.py           # Запись, права доступа и блокировка
│   └── migration.py         # Перенос старых каталогов
├── tests/                   # Модульные и интеграционные проверки
├── compose.yaml
├── nginx/
├── site/
├── template.env
├── .env                     # Локальные настройки, не в Git
└── *_data/                  # Существующие данные, не в Git
```

Compose, сайт, конфигурация Nginx, тесты и данные остаются на прежних местах. Python-модули из `src/` не запускаются отдельно; устанавливать пакет через pip или создавать виртуальное окружение не требуется.

## Подготовка Traefik и DNS

Используйте работающий стек `available/traefik`. В нём уже объявлены:

- HTTPS entrypoint `websecure` на TCP/443;
- resolver `letsencrypt` с DNS challenge Cloudflare;
- Docker provider и внешняя сеть `traefik`.

Менять статическую конфигурацию Traefik для Xray не требуется. DNS API token для выпуска сертификата настраивается в `.env` **Traefik**, в переменной `CLOUDFLARE_API_TOKEN`, а не в `.env` Xray. Он должен иметь права на DNS challenge нужной зоны. Серое облако не мешает выпуску сертификата через DNS challenge.

Если ваш базовый домен — `example.com`, создайте DNS-запись:

| Тип | Имя | Значение | Проксирование Cloudflare |
|---|---|---|---|
| A | `xray` | Публичный IPv4 сервера с Traefik | **DNS only, серое облако** |

Не добавляйте AAAA, если IPv6 не настроен на этом сервере. Удалите или исправьте старую AAAA-запись: иначе часть клиентов будет обращаться не туда. TCP/443 должен быть доступен извне и опубликован **только Traefik**, а не Xray. Дополнительные порты для Xray в firewall открывать не нужно.

Убедитесь, что общие сети существуют:

```bash
docker network inspect traefik
docker network inspect apprise_notification
```

Если сеть отсутствует, создайте соответствующую командой `docker network create ИМЯ_СЕТИ`. Traefik должен быть подключён именно к сети `traefik`. Для уведомлений Restic нужен общий сервис Apprise.

## Настройки .env

| Переменная | Назначение |
|---|---|
| `CONTAINER_NAME` | Обязательное имя экземпляра, например `xray`; контейнер будет `xray_main` |
| `DOMAIN` | Обязательный базовый домен, например `example.com`; публичное имя автоматически станет `xray.example.com` |
| `RESTIC_PASSWORD` | Обязательный непустой пароль репозитория Restic; задайте случайный и сохраните отдельно |
| `TZ` | Часовой пояс расписания Restic, по умолчанию `Europe/Moscow` |

В `DOMAIN` не указывайте `https://`, порт, путь, завершающую точку и префикс `xray.`. Для IDN используйте ASCII/Punycode. Значение должно совпадать с вашей DNS-зоной; `example.com` в шаблоне нужно заменить.

`python3 xray.py setup` получает параметры через `docker compose config`, не исполняя `.env` как shell-код. Переменные окружения имеют приоритет над `.env`; сохраняйте постоянные настройки в `.env`, чтобы генерация и последующий запуск использовали один домен и имя контейнера. Старые `TARGET_HOST`, `SERVER_IP` и `XRAY_PORT` больше не используются — удалите их при переходе.

Изменение `.env` не переписывает существующий JSON. При смене `DOMAIN` необходимо согласованно изменить адрес, SNI и Host в клиентском JSON и ссылке. Имена router/service `xray` и `xray-site` глобальны для Docker provider Traefik: этот шаблон рассчитан на один такой стек на экземпляр Traefik.

## Первая установка

Нужны Linux, Python 3.10+, Docker Engine, Compose с поддержкой `config --format json` и клиент с поддержкой **VLESS + XHTTP + TLS**. Python-код использует только стандартную библиотеку, включая Linux-механизмы блокировки и открытия файлов без перехода по ссылкам. Для генерации больше не нужны curl и внешний сервис определения IP. Сохраняйте структуру каталогов репозитория: Compose использует общий шаблон `available/restic/restic-compose-base.yaml`.

1. Создайте DNS-запись `xray.ваш-домен` на IP сервера. В Cloudflare оставьте **DNS only — серое облако**. Если IPv6 не настроен, не добавляйте AAAA.
2. Из `available/xray` выполните `cp template.env .env` и `chmod 600 .env`. Укажите базовый `DOMAIN` без `xray.` и задайте случайный `RESTIC_PASSWORD`.
3. Выполните:

   ```bash
   docker compose config --quiet
   python3 xray.py setup
   python3 xray.py check
   python3 xray.py up
   python3 xray.py status
   ```

Генерируются `${CONTAINER_NAME}_data/config/config.json`, `${CONTAINER_NAME}_data/client/client.json` и `${CONTAINER_NAME}_data/client/import-link.txt`. Перенесите клиентский JSON на устройство с Xray или импортируйте ссылку в клиент с поддержкой XHTTP и TLS. Клиент проверяет сертификат; не включайте `allowInsecure`.

`python3 xray.py setup` скачивает образ Xray и проверяет JSON одноразовым контейнером, но не запускает постоянные сервисы и не выпускает сертификат сам. После `python3 xray.py up` выпуском и продлением сертификата занимается Traefik. Дождитесь успешного выпуска, прежде чем проверять подключение клиента.

Клиент использует SNI и HTTP Host `xray.${DOMAIN}`, ALPN `h2,http/1.1` и режим XHTTP `packet-up` для совместимости с reverse proxy. Сервер принимает XHTTP в режиме `auto`; путь и UUID клиента совпадают с серверными. Не добавляйте buffering, переписывание пути, BasicAuth или обязательную авторизацию веб-панели к router Xray: это нарушит протокол. Клиентский UUID остаётся средством аутентификации VLESS.

### Управление стеком

Единая точка входа — `python3 xray.py`. Команды можно вызывать из любого рабочего каталога, указав путь к скрипту: Docker запускается из каталога стека, пути данных и имя Compose-проекта сохраняются.

Справка: `python3 xray.py --help` и `python3 xray.py КОМАНДА --help`; для неё Docker и `.env` не нужны. Скрипт также можно запускать как `./xray.py`. Стандартные переменные окружения Compose, в том числе `COMPOSE_PROJECT_NAME` и `COMPOSE_FILE`, сохраняют своё действие: используйте одинаковое окружение при генерации и управлении существующим стеком.

| Команда | Назначение |
|---|---|
| `setup` | Создать новые реквизиты и проверить Xray, не запуская стек |
| `check` | Проверить Compose, Xray и Nginx без перегенерации |
| `up [СЕРВИС ...]` | Запустить весь стек либо выбранные сервисы |
| `down` | Остановить стек без удаления томов и данных |
| `status` | Показать состояние сервисов |
| `logs [--tail 50] [--follow] [СЕРВИС ...]` | Показать логи |
| `migrate-layout` | Перенести старые `config/` и `client/`, не преобразуя JSON |

Допустимые сервисы: `app`, `site`, `backup_restic__xray`, `prune_restic__xray`, `check_restic__xray`. `up` не выполняет проверки автоматически: перед обновлением используйте `check`. Команда `check` запускает одноразовые контейнеры, но не постоянные сервисы и не проверяет DNS или сертификат. Запуск сервисов Restic сохраняет их штатное поведение, включая проверку репозитория при запуске.

Ошибки Docker выводятся без содержимого конфигураций; ненулевой код передаётся вызывающему процессу (коды вне диапазона 1–125 заменяются на 1). **`logs` намеренно показывает исходный вывод контейнеров**, в котором могут оказаться реквизиты: не публикуйте его без проверки.

### Статический сайт

Заглушка находится в `site/index.html`, конфигурация Nginx — в `nginx/default.conf`. Каталог сайта и конфигурация смонтированы только для чтения; Nginx работает без привилегий, с read-only корневой файловой системой и временным `/tmp`. EntryPoint образа заменён прямым запуском Nginx, чтобы стартовые скрипты не пытались менять конфигурацию.

Для изменения содержимого отредактируйте файлы в `site/`: обычные изменения файлов доступны без пересборки образа. После изменения конфигурации выполните:

```bash
docker compose run --rm --no-deps site -t
docker compose up -d --force-recreate site
```

Отсутствующие файлы возвращают `404`, листинг каталогов отключён. Монтируется только каталог `site/`, а не весь стек или каталог данных. Не копируйте туда `.env`, JSON, UUID и импорт-ссылки: содержимое сайта публично. Сайт и прокси запускаются независимо; отказ одного backend не должен нарушать работу другого.

### Данные и безопасность

Для `CONTAINER_NAME=xray` структура и права такие:

```text
xray_data/                    # 700
├── config/                   # 755
│   └── config.json           # 644, содержит UUID доступа
└── client/                   # 700
    ├── client.json           # 600, SOCKS5 на 127.0.0.1:10808
    └── import-link.txt       # 600, ссылка vless://
```

Серверный JSON читает непривилегированный процесс контейнера через read-only bind mount; родительский каталог закрыт для других обычных пользователей хоста. Контейнер сохраняет ограничения `read_only`, `no-new-privileges`, `cap_drop: ALL` и временный `/tmp`. Отсутствующий JSON не заменяется автоматически каталогом.

Не публикуйте JSON, ссылку и `.env`: в них данные доступа. Они исключены из Git. Повторная генерация останавливается при наличии любого из трёх файлов, включая повреждённую символьную ссылку. Если проверка Xray после генерации завершилась ошибкой, исправьте сохранённые файлы и повторите тест вручную — не удаляйте реквизиты ради повторного запуска `python3 xray.py setup`.

`setup` и `migrate-layout` используют общую неблокирующую блокировку `.xray.lock`: второй одновременный запуск завершается ошибкой. Файл исключён из Git и остаётся после завершения команды; наличие файла само по себе не означает активную блокировку. Не удаляйте его во время работы команды. Символьные ссылки в каталогах записи запрещены, новые файлы создаются исключительно без перезаписи существующих. Блокировка согласует операции этого инструмента, но не защищает от ручного изменения данных другим процессом.

Если скачивание образа завершилось ошибкой, реквизиты ещё не создавались. Если ошибка возникла во время записи, часть файлов может уже существовать: они сохраняются для проверки и восстановления вручную. При отказе теста Xray созданный комплект также остаётся на месте. После исправления используйте `python3 xray.py check`, а не повторную генерацию.

## Существующая установка

### Обновление управляющих скриптов

Сохраните защищённую копию `.env` и `${CONTAINER_NAME}_data`, затем обновите файлы проекта из Git. Вместо прежнего Bash-сценария используется `xray.py` с каталогом `src/`; данные, пути Compose и Restic не перемещаются. Не заменяйте существующий `.env` шаблоном и не запускайте `setup`: прежние UUID, путь XHTTP и клиентские профили остаются действительными.

```bash
python3 xray.py check
python3 xray.py status
```

Само обновление Python-кода не требует перезапуска контейнеров. Если одновременно изменён Compose или конфигурация сервисов, после успешной проверки выполните `python3 xray.py up app site` и проверьте соединение прежним клиентским профилем. Перенос старых корневых `config/` и `client/` нужен только для соответствующей старой структуры, а не для обычного обновления скриптов.

### Добавление сайта к работающей установке XHTTP + TLS

Перегенерировать реквизиты не нужно. До обновления проверьте в серверном JSON `inbounds[].streamSettings.xhttpSettings.path`: используемый путь должен начинаться с `/api/`. Если путь вручную изменён и имеет другой префикс, заранее адаптируйте правило router `xray` под него, сохранив более высокий приоритет и исключив пересечение с файлами сайта. Клиентский профиль менять не требуется.

1. Сохраните защищённую копию `${CONTAINER_NAME}_data` и `.env`.
2. Обновите `compose.yaml`, добавьте каталоги `nginx/` и `site/`. Не меняйте серверный JSON и клиентские файлы, не запускайте `python3 xray.py setup` повторно.
3. Из каталога стека выполните:

   ```bash
   python3 xray.py check
   python3 xray.py up app site
   ```

4. Проверьте сайт и соединение прежним клиентским профилем по инструкции ниже. При пересоздании `app` активные подключения могут прерваться.

### Переход со старой установки REALITY

**Старый REALITY JSON не подходит для нового Compose. Не запускайте новый стек со старой конфигурацией без её адаптации.** `python3 xray.py setup` не перезаписывает существующие файлы.

Для сохранения доступа сначала сделайте защищённую копию данных и остановите старый Xray. В серверном JSON сохраните UUID и путь XHTTP, смените порт inbound на 8080, `streamSettings.security` на `none` и удалите `realitySettings`. Если прежний путь находится вне `/api/`, адаптируйте правило Traefik, как описано выше. В клиентском JSON укажите адрес `xray.${DOMAIN}`, порт 443, `security: tls`, `tlsSettings.serverName` с тем же доменом и включённую проверку сертификата; удалите `realitySettings`, сохраните UUID и путь. Поставьте клиенту режим XHTTP `packet-up` и обновите импорт-ссылку: `security=tls`, `sni=xray.${DOMAIN}`, `host=xray.${DOMAIN}`, без `pbk` и `sid`. Новую конфигурацию обязательно проверьте перед запуском.

Рекомендуемый порядок:

1. До обновления файлов остановите старый стек его прежней командой `docker compose down`. Это освободит опубликованный Xray порт; если старый Xray занимал 443, после остановки запустите Traefik. Сам Traefik при миграции останавливать не нужно.
2. Сохраните защищённую копию всего каталога данных и `.env`. После обновления добавьте `DOMAIN`, оставьте прежние `CONTAINER_NAME` и `RESTIC_PASSWORD`. Не заменяйте существующий `.env` целиком шаблоном: это может потерять пароль резервных копий.
3. Если данные ещё в старых `config/` и `client/`, перенесите их в `${CONTAINER_NAME}_data/`, только если там нет других данных. Не смешивайте разные установки. Для установки с именем `xray`:

   ```bash
   python3 xray.py migrate-layout
   ```

   Команда получает `CONTAINER_NAME` через Compose, требует все три штатных файла и отказывается от переноса, если назначение уже существует (включая символьную ссылку). Исходные каталоги и штатные файлы не могут быть символьными ссылками. Содержимое файлов, UUID и пути XHTTP не меняются; права приводятся к значениям из раздела безопасности. Дополнительные файлы переносятся вместе с каталогами, их права не меняются. Команда не останавливает контейнеры и не преобразует REALITY в TLS.

   Проверки конфликтов выполняются до переноса. При системном сбое после начала перемещения данные не удаляются: проверьте исходные каталоги и `${CONTAINER_NAME}_data`, восстановите согласованную структуру и права вручную либо из защищённой копии. Не запускайте `setup` поверх частичной миграции.

   Если остался контейнер первоначальной установки `xray-private`, убедитесь, что это именно старый Xray, и остановите и удалите его отдельно (`docker stop xray-private`, затем `docker rm xray-private`).
4. Вручную адаптируйте JSON по описанию выше. Пример серверного `streamSettings` (вместо `/api/ВАШ_ПУТЬ` сохраните исходный путь):

   ```json
   {
     "network": "xhttp",
     "security": "none",
     "xhttpSettings": {"path": "/api/ВАШ_ПУТЬ", "mode": "auto"}
   }
   ```

   Внешний порт клиента — **443**, внутренний порт серверного inbound — **8080**. В `settings.clients` и `settings.vnext[].users` сохраните исходный UUID.

   Клиентский `streamSettings` для `DOMAIN=example.com`:

   ```json
   {
     "network": "xhttp",
     "security": "tls",
     "tlsSettings": {
       "serverName": "xray.example.com",
       "fingerprint": "firefox",
       "alpn": ["h2", "http/1.1"],
       "allowInsecure": false
     },
     "xhttpSettings": {
       "host": "xray.example.com",
       "path": "/api/ВАШ_ПУТЬ",
       "mode": "packet-up"
     }
   }
   ```

   В импорт-ссылке сохраните UUID и URL-кодированный исходный путь. Кроме `security=tls`, `sni` и `host`, укажите `type=xhttp`, `mode=packet-up`, `fp=firefox`, `alpn=h2%2Chttp%2F1.1`, `encryption=none`. Удалите REALITY-параметры `pbk`, `sid`, `spx`. Старые ключи REALITY для TLS не нужны; UUID и путь можно сохранить, но клиентские профили необходимо обновить.
5. Выполните проверки из следующего раздела, затем `python3 xray.py up`. Передавайте обновлённые клиентские файлы только защищённым способом. **Не запускайте `python3 xray.py setup` для миграции**: автоматического преобразования старых конфигураций нет.

```bash
python3 xray.py check
python3 xray.py logs --tail 50 app site
```

При `DOMAIN=example.com` проверьте DNS и сертификат (без отключения проверки сертификата):

```bash
dig +short xray.example.com A
dig +short xray.example.com AAAA
curl -v --connect-timeout 10 https://xray.example.com/
curl -I --connect-timeout 10 https://xray.example.com/
curl -i --connect-timeout 10 https://xray.example.com/missing-file.txt
```

На `/` ожидается `200` с HTML-заглушкой (для HEAD — без тела), на отсутствующий файл — `404` от Nginx. Для проверки статических ресурсов добавьте файл в `site/` и запросите его URL. Случайный несуществующий путь `/api/...` должен обрабатываться Xray, а не возвращать HTML-заглушку; один лишь статус `404` не доказывает правильность выбора backend.

Успешная TLS-проверка и даже ответ HTTP не доказывают работу прокси. При ошибке сертификата смотрите логи **контейнера Traefik** и права DNS API token. `502` на сайте указывает на Nginx или сеть; для `/api/...` — на внутренний порт 8080, h2c, конфигурацию Xray или сеть `traefik`. JSON-тест не проверяет DNS, сертификат и доставку трафика.

На клиентском устройстве запустите Xray с `client.json`, затем:

```bash
curl --proxy socks5h://127.0.0.1:10808 https://ifconfig.me
```

В ответе должен быть внешний IP сервера Xray. Для временной диагностики измените серверный `log.loglevel` с `none` на `warning`, выполните `docker compose up -d --force-recreate app` и `docker compose logs --since=2m app`. После проверки верните `none`. Не публикуйте UUID и случайный путь в логах или скриншотах; access log Traefik, если его включить, может записывать путь XHTTP.

На тестовом стенде проверьте одновременную загрузку сайта и работу прежнего прокси-профиля. Затем по очереди остановите `site` и убедитесь, что прокси работает; запустите `site`, остановите `app` и проверьте сайт. После проверки запустите оба сервиса командой `docker compose up -d app site`. Эти проверки намеренно прерывают обслуживание соответствующего сервиса.

Watchtower для Xray разрешён меткой `com.centurylinklabs.watchtower.enable: "true"`. Автоматическое обновление произойдёт, если работающий Watchtower настроен обрабатывать этот контейнер. `latest` — изменяемый тег, возможны несовместимые изменения; Watchtower не выполняет описанные здесь проверки совместимости и резервное копирование перед обновлением. Для обновлений только вручную сначала отключите метку. Ручное обновление выполняйте после резервного копирования и проверки совместимости клиентов:

```bash
docker compose pull app
python3 xray.py check
python3 xray.py up app
```

## Резервное копирование

Restic сохраняет весь `${CONTAINER_NAME}_data`, включая настройки клиентов. Репозиторий — `/backup/ssd/restic/${CONTAINER_NAME}_backups`, каталог восстановления — `${CONTAINER_NAME}_data/backup_restore`. `.env` и пароль храните отдельно. Сертификат находится у Traefik, не у Xray: резервное копирование его ACME-хранилища нужно проверить и настроить отдельно в стеке Traefik.

Каталоги `site/` и `nginx/` находятся в Git, вне `${CONTAINER_NAME}_data`, и в эту копию Restic не входят. Штатные файлы восстанавливаются из репозитория. Если меняете содержимое сайта только на сервере, организуйте его отдельное резервное копирование. Restic не останавливает контейнер сайта.

**Restic останавливает `${CONTAINER_NAME}_main` на время копирования и разрывает активные подключения.** Копирование запланировано на 03:30, очистка на 04:00 и проверка на 05:15 по `TZ`; проверка также выполняется при запуске своего сервиса. Общий шаблон использует Docker socket с привилегированным доступом к Docker хоста. При восстановлении сначала остановите стек, восстановите данные и права доступа, проверьте JSON и лишь затем запускайте сервисы. Не запускайте генерацию поверх восстановленных данных.

## Проверки разработки

Тесты запускаются из корня репозитория. Временные данные размещаются в `/tmp/opencode`; создайте этот каталог заранее, если его нет:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s available/xray/tests -v
git diff --check
```

При установленном Ruff дополнительно выполните `ruff check available/xray` и `ruff format --check available/xray`. Ruff нужен только для разработки, не для установки или управления стеком.

`test_cli.py`, `test_configuration.py`, `test_storage.py`, `test_migration.py` и `test_project.py` — модульные и локальные проверки без Docker и сети. `test_setup.py` — отдельная интеграционная группа с настоящим разбором Compose, без скачивания образов и запуска контейнеров. Без Docker CLI эта группа пропускается; если CLI установлен, нужен и плагин Compose.

Например, интерфейс можно проверить отдельно:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s available/xray/tests -p test_cli.py -v
```

Проверяются TLS-настройки, импорт-ссылка, маршруты Traefik, отсутствие опубликованных портов, read-only монтирования, права файлов, защита существующих реквизитов, конкурентная блокировка и перенос старых каталогов. Ошибки Docker и команды управления проверяются с подменой вызовов. Формат генерируемого пути `/api/<24 hex>` проверяется тестом генератора; тест структуры контролирует отсутствие Bash-файлов и единственную точку входа в корне.

На отдельном стенде дополнительно выполните первую установку с тестовым `.env`, `check`, `up` и `status`; затем обновите файлы проекта и убедитесь, что прежний клиентский профиль продолжает работать без запуска `setup`. Nginx, реальную маршрутизацию HTTP, выпуск сертификата, сквозное подключение через ваш домен и восстановление Restic проверяйте только на таком стенде. Автоматические тесты не подтверждают эти внешние интеграции.
